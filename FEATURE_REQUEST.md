# Feature Requests — Running Plan

A living backlog of feature ideas for Silent Whisper. This is a planning document, not an implementation log — see `PROJECT_PLAN.md` Section 11 for what's actually been built.

## How this document is maintained

- Whenever a new feature is requested, a design is thought through (what changes, where, how it fits the existing authorization/audit/rate-limiting conventions in `PROJECT_PLAN.md`) and added below as its own entry, in the format under "Entry format."
- After each addition, every entry is re-ranked by utility and implementation dependency — most useful first unless a prerequisite should land earlier. Rank changes are expected over time as the app's shape changes; nothing here is permanent.
- An entry moves to **Done** (with a pointer to the `PROJECT_PLAN.md` Section 11 log entry that implemented it) once it ships, rather than being deleted — keeps the history of what was considered and why.
- Nothing in this document is authorization to build it. Design-only until explicitly requested.

## Entry format

```
### N. Title

**Status**: Proposed | Planned | Done
**Utility**: one line on why this matters / who it's for
**Origin**: how this came up (a request, a gap found during other work, etc.)

Design: what changes, where, how it's authorized/audited/tested, matching
existing PROJECT_PLAN.md conventions. Enough detail that implementation is
a matter of execution, not re-deciding the approach.
```

### 1. Minimal CI workflow

**Status**: Proposed
**Utility**: `ARCHITECTURE_REVIEW_(Claude).md` calls this "the single cheapest fix on this list" (P0 Recommendation 1) — nothing currently gates a broken build or a failing test from reaching `main`. Confirmed still true: no `.github/workflows` directory exists at all. This is the complementary half of "the deploy loop" entry (already shipped): that entry stops a *stale* container from being deployed; this stops a *broken* one from ever being deployable in the first place.
**Origin**: `ARCHITECTURE_REVIEW_(Claude).md` P0 Recommendation 1 (2026-07-17), re-confirmed against the live repo on 2026-07-18.

Design:
- New `.github/workflows/ci.yml`, triggered on every push to `main` and every pull request targeting it. Two independent jobs so a frontend-only or backend-only PR isn't blocked waiting on the other:
  - **`backend`**: a `postgres` service container (`pgvector/pgvector:pg16`, matching `docker-compose.yml`'s own image choice so `CREATE EXTENSION vector` works — plain `postgres:16-alpine` would fail migration `0009`), `POSTGRES_DB: silent_whisper_test` directly (no separate create-database step needed). Steps: checkout, `actions/setup-node@v4` (node 20, matching every `Dockerfile`'s `FROM node:20-alpine`), `npm ci` in `backend/`, `npm run migrate` (creates the schema *and* the `app_runtime_user` role — see `database/migrations/0007_grants.js`), `npm test`.
  - **`frontend`**: checkout, setup-node, `npm ci` in `frontend/`, `npm run test:unit`, `npm run build`.
  - **Deliberately out of scope**: `frontend/e2e` (Playwright) — needs a live Ollama instance, real Docker Compose stack, cached browser binaries, and careful rate-limiter batching (`RUNBOOK.md`'s Integration Tests section documents exactly why a single unbatched run 429s). That's a meaningfully bigger lift than "run the existing unit/integration suites," and Claude review's own P0 framing only ever asked for `npm test`/`npm run test:unit`/`npm run build` — e2e-in-CI is a separate future entry if wanted, not bundled into this one.
- **Env vars for the `backend` job** (`PGHOST: localhost`, `PGPORT: 5432`, `PGUSER`/`PGPASSWORD` matching the service container's admin credentials, `PGDATABASE: silent_whisper_test`, `APP_DB_USER`, `APP_DB_PASSWORD`, `JWT_SECRET`) come from **GitHub Actions repository secrets** (`secrets.CI_PGPASSWORD`, `secrets.CI_APP_DB_PASSWORD`, `secrets.CI_JWT_SECRET`), not literals in the workflow file — `PROJECT_PLAN.md` Section 3 says exactly this for any future CI secret ("reference secrets only as repository secrets... never embed raw values in workflow YAML or IaC templates") with no carve-out for "it's only a throwaway CI database," so this follows that literally rather than deciding it's a special case. These three repository secrets need to be added once (any generated value works — nothing in the ephemeral CI Postgres container persists or is reachable outside that one workflow run) before the workflow can pass.
- **No schema/authz/audit implications** — this is CI plumbing only, one new file (`.github/workflows/ci.yml`).
- **Tests**: none needed for the workflow file itself; its "test" is that it actually goes green on the PR that introduces it, and red on a PR that deliberately breaks a test (worth confirming once during implementation, then reverting the deliberate break).

### 2. Shift+Enter inserts a line break in the message composer

**Status**: Proposed
**Utility**: The message composer in both the main channel view and the thread sidebar is a plain HTML `<input>`, which cannot hold a newline character at all — there is no way today to compose a multi-line message (a short code snippet, a checklist written as plain text before formatting it as a task list, a multi-paragraph update) without sending several separate short messages. This is a universal, high-frequency papercut affecting every message ever typed, not a niche gap.
**Origin**: User feature request (2026-07-25).

Design:
- **Root cause, not just a missing keybinding**: `frontend/src/components/ChannelView.jsx:792-818`'s composer and `frontend/src/components/ThreadSidebar.jsx:333-339`'s reply composer are both `<input>` elements — HTML `<input>` strips/rejects newline characters outright (typing, pasting, or programmatically setting a `\n` into an `<input>`'s value is not possible in any browser), so this cannot be solved by a keydown handler alone. Both must become `<textarea>` elements.
- **Rendering already supports it**: message bubbles already render with `whiteSpace: 'pre-wrap'` (`ChannelView.jsx:181`'s `messageContent` style; `ThreadSidebar.jsx`'s `:58`/`:121` bubble-content styles), and `renderMessageContent()` (`markdown.jsx`) does not collapse `\n` — so once a message actually contains a newline, it already displays correctly with zero rendering changes. Backend validation needs no change either: `assertMessageContent` (`validation.js:97-105`) only checks non-empty and `MAX_MESSAGE_LENGTH` (10,000 chars), with no character-class restriction — multi-line content already passes today, unreachable only because the composer itself can't produce it.
- **Key handling — `ChannelView.jsx`**: `handleComposerKeyDown` (`:616-647`) already intercepts `Enter`/`Tab`/arrow keys when an `[[Entity` or `@mention` suggestion dropdown is open (`activeKind`), calling `preventDefault()` and accepting the highlighted suggestion instead of submitting. That branch takes priority unchanged — Enter or Shift+Enter while a dropdown is open still accepts the suggestion, never inserts a newline or sends, matching today's behavior exactly. Below that branch, a new rule: `Enter` without `Shift` calls `e.preventDefault()` and submits (mirroring what `<input>`'s native implicit-submit used to do for free); `Shift+Enter` does nothing (`textarea`'s own native behavior on Enter — inserting a newline at the caret — already does the right thing once nothing calls `preventDefault()` on it).
- **Key handling — `ThreadSidebar.jsx`**: the reply composer (`:333-339`) has no `onKeyDown` handler at all today — sending currently relies purely on `<input>`'s native submit-on-Enter. Since a `<textarea>` never submits its form on Enter natively, this composer now needs its own new keydown handler, added from scratch: the same "bare Enter submits, Shift+Enter doesn't" rule as above, with no dropdown-interception branch to preserve (this composer has no autocomplete).
- **Auto-grow height**: a fixed single-line `<input>` height doesn't fit multi-line content. New behavior: the textarea starts at its current single-line height, grows automatically as content wraps or newlines are added (measured via `scrollHeight` on every `onChange`, applied as an inline `height` style), capped at a maximum (proposed: 6 lines' worth, matching a common chat-composer convention), beyond which it scrolls internally rather than growing further — `resize: none` (auto-grow, not user-draggable, distinct from `EntityDetailsPanel.jsx`'s `styles.textarea`'s `resize: 'vertical'`, which is a form field, not a chat composer). No existing auto-grow textarea component exists in this codebase to reuse; this is new, small, local logic in each composer.
- **ARIA note, flagged rather than silently carried over**: the `<input>`'s `role="combobox"`/`aria-autocomplete="list"`/`aria-controls`/`aria-activedescendant` attributes (`ChannelView.jsx:807-817`) implement the entity/mention-autocomplete pattern. The ARIA combobox pattern is authored around a single-line textbox; applying it to a multi-line `<textarea>` is a minor, known deviation from the strict spec, not a functional break — the actual keyboard/screen-reader interaction (arrow-key navigation, Enter-to-accept, Escape-to-dismiss) is unaffected since it's implemented entirely in `handleComposerKeyDown`, not by the native role. Carried over unchanged rather than redesigned; worth a dedicated a11y pass later if it's ever flagged in practice, matching how this app already tracks a couple of known, accepted contrast gaps elsewhere (`README.md`'s Known Issues) rather than blocking on every open a11y question.
- **Trimming already correct**: `onSend(draft.trim())` (`ChannelView.jsx:503`) and `onSendReply(draft.trim())` (`ThreadSidebar.jsx:171`) already trim before sending — a message made of only newlines/whitespace is already blocked by the existing `disabled={!draft.trim()}` Send-button guard (`ChannelView.jsx:868`, `ThreadSidebar.jsx:340`) and by `.trim()` stripping leading/trailing blank lines before the request is even made. No new trimming logic needed.
- **No backend change at all** — this is a pure frontend/composer change; `MAX_MESSAGE_LENGTH`, `assertMessageContent`, message creation, and every downstream consumer of `messages.content` (entity linking, mention extraction, embeddings) already handle multi-line content correctly, since none of them assume single-line input.

**Tests**: `frontend/e2e/workflows.spec.js` needs every composer locator updated from `input[placeholder...]` to `textarea[placeholder...]` (at minimum `input[placeholder^="Message #"]` and `input[placeholder="Reply in thread"]`, plus any test that fills the composer elsewhere in the file) — a mechanical but required sweep, not optional. New e2e coverage: Shift+Enter inserts a newline without sending (message count in the feed stays the same, composer still has focus/content); bare Enter still sends; Enter while an entity/mention dropdown is open still accepts the suggestion and does not send or insert a newline (regression coverage for the existing behavior, not just the new one); a sent multi-line message renders with visible line breaks in the feed. Frontend unit coverage is limited to whatever pure logic this introduces (e.g., an extracted auto-grow height calculation, if it's written as a testable pure function rather than inline in the component, matching this codebase's established "extract pure logic for direct testing, no jsdom" convention).

### 3. Obsidian-style bold-italic and highlight formatting in messages

**Status**: Proposed
**Utility**: Rounds out this app's Markdown formatting to match Obsidian's own inline-emphasis notation, which is the explicit ask — a user coming from Obsidian (or any CommonMark-family editor) already reaches for `***word***` to emphasize strongly and `==word==` to flag something for a reader's attention, and today one of those silently renders wrong (see Design) and the other does nothing at all.
**Origin**: User feature request (2026-07-26): "Obsidian-style markdown notation for formatting text (italic, bold, bold italic, and highlight) in channels and threads."

Design:
- **Two of the four are already shipped, and already match Obsidian's own syntax exactly** — worth stating plainly so this entry isn't mistaken for a bigger gap than it is. `frontend/src/markdown.jsx`'s existing tokenizer (FEATURE_REQUEST.md's "Basic Markdown formatting" entry, Done) already handles `**bold**`/`__bold__` (`BOLD_STAR_RE`/`BOLD_UNDERSCORE_RE`, `:36,45`) and `*italic*`/`_italic_` (`ITALIC_STAR_RE`/`ITALIC_UNDERSCORE_RE`, `:46-47`), including the underscore variants' word-boundary guard so `snake_case_names`/`__init__` aren't accidentally emphasized (`:37-44`). This entry's real scope is the two genuinely missing tokens: **bold-italic** (`***text***`/`___text___`) and **highlight** (`==text==`).
- **Bold-italic isn't just "add a regex" — it's a precedence bug fix.** `applyInlinePasses` (`:343-353`) runs `BOLD_STAR_RE` before `ITALIC_STAR_RE`, and each pass only re-scans the plain-text left over from the one before it. Run today's tokenizer on `***text***`: `BOLD_STAR_RE`'s lazy `\*\*([^\n]+?)\*\*` matches greedily-enough to consume `**` + `*text` + `**` (landing on the *first* available closing `**`, which is one character short of where a human would expect), leaving one stray `*` before "text" inside the `<strong>` and two stray literal `*` characters after it — a visibly broken render, not a graceful "unsupported" fallback. A new `BOLD_ITALIC_STAR_RE = /\*\*\*([^\n]+?)\*\*\*/g` (and `BOLD_ITALIC_UNDERSCORE_RE`, with the same `(?<!\w)`/`(?!\w)` guard `BOLD_UNDERSCORE_RE`/`ITALIC_UNDERSCORE_RE` already use) must run in `applyInlinePasses` **before** the existing bold and italic passes — order in this pipeline is precedence, exactly like the file's own header comment already documents for links-before-everything-else. Rendered as `<strong><em>{content}</em></strong>`, reusing `processHighlightsWithin` for the same one-level-deep entity/mention nesting `boldToNode`/`italicToNode` already get (`:301-306`) — so `***ping @bob about [[Server Alpha]]***` still highlights the inline tokens, matching existing behavior rather than inventing a richer nesting model for just this one token.
- **Highlight is a genuinely new token, not a fix.** `MARK_RE = /==([^\n=]+?)==/g`, rendered as a real `<mark>` element (semantically correct HTML for "highlighted for reference," and — same reasoning as every other token in this file — a plain React element, never `dangerouslySetInnerHTML`). Slots into `applyInlinePasses` alongside the bold/italic passes (order relative to them doesn't matter for correctness, since `=` shares no characters with `*`/`_`; recommended right after the italic passes, before entities/mentions, mirroring bold/italic's own position) and gets the same `processHighlightsWithin` nested pass they get, for the same reason.
- **Naming trap, flagged explicitly so it isn't repeated during implementation**: this file already has a `highlightOptions` parameter and a `processHighlightsWithin` function (`:290-299`) — these name the *existing* "give entities/mentions their own styled treatment inside bold/italic content" mechanism, unrelated to Obsidian-style `==highlight==`. Naming the new token/function `MARK_RE`/`markToNode` (not `HIGHLIGHT_RE`/`highlightToNode`) avoids a same-word collision with an unrelated existing concept in the same file.
- **Styling**: new `styles.mark`/`styles.markOnMine` entries (`:119` region), following the exact pattern `entity`/`entityOnMine`, `mention`/`mentionOnMine`, `link`/`linkOnMine` already establish (`:120-144`) — a `variant === 'mine'` bubble already sits on a saturated background color, so `<mark>`'s browser-default yellow background needs a deliberately chosen pair of theme-aware colors (both light/dark and default/on-mine) rather than relying on the UA stylesheet default, matching how every other inline token in this file already avoids browser defaults in favor of `var(--*)` custom properties.
- **No composer affordance, no backend change** — same shape as the original Basic Markdown entry: purely typed-markdown-in, rendered-out, no toolbar/keyboard-shortcut work (none exists for the already-shipped bold/italic either, so adding one for just these two new tokens would be inconsistent). `assertMessageContent` (`validation.js:97-105`) already permits `*`/`_`/`=` in content with no character-class restriction, and `embeddingWorker.js` already embeds raw `content` including markdown syntax — both already correct for these two new tokens with zero change needed, the same conclusion the original entry reached for `**`/`*`/`_`.
- **Explicitly out of scope**: recursive nesting of the new tokens inside each other or inside existing bold/italic (e.g. `**==text==**` or `==***text***==`) — the existing tokenizer doesn't support arbitrary recursive nesting for *any* pair of tokens today (only entities/mentions get a nested pass, per the file's own header comment), and this entry keeps that same one-level-deep convention rather than quietly expanding it. Worth a dedicated future entry if genuinely wanted, not assumed here.

**Tests**: `frontend/src/markdown.test.jsx` needs new `describe` blocks mirroring the existing `bold`/`italic` ones: bold-italic via both `***`/`___` delimiters, malformed/unclosed cases (`***text**`, `***text*`) falling back to literal text rather than a broken partial render (the specific failure mode this entry is fixing), and a regression case proving `***text***` no longer produces the stray-asterisk output described above. Highlight: basic `==text==`, composition with mentions/entities inside it, and a malformed/unclosed case. Both new tokens need a `variant: "mine"` case, matching the existing per-token pattern in this file.

### 4. Focus: a finite, responsibility-ranked work-triage view (formerly "Channel attention and health views")

**Status**: Proposed — ground-up redesign of the original entry below; nothing described in this entry is built yet. It is written against the codebase as of 2026-07-24 (the "Ephemeral direct messages" entry is the most recent Done item) and calls out by name every existing piece it reuses, and every place the schema/AI layer has no equivalent today.
**Utility**: A conventional notification/activity panel (this app's own `NotificationPanel.jsx` included) answers "something happened." It does not answer "what, of everything that happened, actually needs *you* — your judgment, your response, your approval, your unblock." In a workspace with real message volume, those are very different lists, and the second one is almost always much shorter. Focus is that second list: the smallest set of conversations, decisions, assignments, approvals, questions, blockers, and knowledge developments that require this specific user's action, ranked by responsibility rather than recency, with an honest, non-gamified "caught up" state when the list is empty.
**Origin**: Original entry requested by the user (2026-07-18), "extending Slack/Teams-style catch-up and activity surfaces into a local, project-focused dashboard." Substantially revised by explicit user direction (2026-07-24) to reframe the feature away from activity-recency ranking and toward responsibility-centric, staleness-aware, momentum-tracked work triage — the product direction recorded in this revision's own request, not inferred.

#### Status

Proposed. No schema, route, service, or UI file for this feature exists in the repository today. This entry is a full specification intended for direct implementation by a later session, phased per "Phased delivery" below. Every reference to an existing file, table, column, or convention in this entry has been checked against current source (see the specific paths cited throughout); every place this design needs something the codebase does not yet have is called out explicitly under "Data and backend considerations" and "Open implementation questions" rather than assumed into existence.

#### Product rationale

Slack-style products optimize, whether they mean to or not, for re-engagement: unread badges, activity feeds sorted by recency, and "since your last visit" framing all reward opening the app and scanning, not resolving anything in particular. That model fits a large, high-recall product where more attention is generically good for the business. It does not fit what this application's own design already prioritizes — a deterministic-first, audit-honest, non-manipulative tool for a project team (`CLAUDE.md`'s rules of engagement, `PROJECT_PLAN.md` Section 3's authorization/audit baseline) — and it actively works against what a project team actually needs, which is fewer stalled things, not more time in the app.

Focus is designed around a different question for every row it shows: not "something happened here," but

1. **What happened?** — a concrete fact (a question was asked, an approval was requested, a checkbox task was assigned, a blocker was confirmed, a decision was reached).
2. **Why does it matter?** — the concrete consequence (it blocks other work, three tasks depend on it, it has been waiting on you for 17 hours).
3. **Why is it being shown to *this* user?** — an authorized, factual reason (you own it, you were asked directly, you follow the entity involved, you participated in the thread) — never an opaque relevance score.
4. **What action would move the work forward?** — a primary action richer than "open the source" (Reply, Approve, Complete, Resolve blocker, Reassign, Acknowledge, and the like — see "Progress and completion model").

The feature explicitly optimizes for reduced manual channel-scanning time, faster responses to explicit requests, fewer stalled conversations, faster blocker resolution, clearer ownership, faster decisions, completed action items, and better cross-channel discovery of developments the user is authorized to see but wouldn't otherwise stumble onto. It explicitly does **not** optimize for notification click-through, messages sent, channel activity, app-open frequency, session duration, or raw unread-count reduction — none of those are tracked as success signals anywhere in this design (see "Metrics"), and the UI section below lists specific patterns (streaks, celebratory effects, oversized cards, vague "AI insight" badges) that are deliberately excluded because they optimize for the wrong thing.

#### Objective

Define a workspace-level **Focus** view that identifies the smallest useful set of items genuinely requiring the current user's judgment, response, or action, ranked by responsibility rather than activity, with explicit staleness, a small explainable momentum model, knowledge-graph-assisted relevance where the graph actually helps, and a real, finite "caught up" state — built entirely on top of this application's existing authorization, audit, rate-limiting, and deterministic-first-then-AI-assisted conventions, never around them.

**On naming**: this entry adopts **Focus** as the working name per the requested product direction. The app's existing vocabulary (`NotificationPanel.jsx`, `mention_notifications`, "Catch Me Up," "Attention" in the original entry) has no strong prior claim on any of "Triage," "Needs You," or "Work Queue" that would override the requested default, so "Focus" is used throughout — `FocusPanel.jsx`, `focus_item_state`, `GET /workspaces/:workspaceId/focus`, etc. A later session is free to bikeshed the literal string before shipping; nothing in this design depends on the name itself.

#### Product principles

- **Responsibility over recency.** Message volume is never, by itself, a ranking input (see "Priority model"). A channel with hundreds of messages since last visit and zero items requiring this user contributes zero Focus rows.
- **Finite and honest.** The view has a real bottom. A user who resolves every explicit obligation sees a calm "caught up" state (see "Progress and completion model"), not backfilled low-value activity to keep the list non-empty.
- **Explainable, not scored.** Every row states its principal reasons in plain language ("why it matters," "why you're seeing this"). An internal numeric/ranking score may exist for ordering purposes, but it is never the explanation shown to the user (Required Design Change 6).
- **Explicit, deterministic, and AI-suggested state are never conflated**, in the data model, the API, or the UI (Required Design Change 7). A confirmed blocker and an AI-guessed possible blocker never look alike.
- **Deterministic first, matching this codebase's own established layering.** Phase 1 and 2 of this feature need no LLM call at all — they are pure SQL over existing/new tables, the same shape as `tasks.js`'s dashboard or `mentionNotificationService.js`'s summary query. AI-assisted detection is Phase 4, gated behind the existing `aiProxyRateLimiter`/`LLM_MAX_CONCURRENT_REQUESTS` machinery, never a prerequisite for the feature being useful.
- **Server time is authoritative for every staleness/momentum computation** (`CLAUDE.md`: "Never trust browser time for anything security- or audit-relevant" — staleness here is not audit-relevant in the forensic sense, but the same principle applies: a client clock must never be able to make an obligation look older or younger than it is).
- **Authorization is structural, not filtered after the fact** — every Focus query is built the same way `entities.js`'s `referencesQuery()`, `tasks.js`'s dashboard query, and `workspaceDigestService.js`'s selection queries already are: an inner join to `channel_members` scoped to the caller, so an unauthorized source contributes zero rows rather than a redacted placeholder (see "Authorization and privacy requirements").
- **Calm, not gamified.** No streaks, no celebratory animation on reaching zero, no color-only urgency signaling (text + accessible status treatment, per Required Design Change 4's own instruction and this app's existing HIG/accessibility pass in `PROJECT_PLAN.md` Section 11).

#### User experience

**Entry point.** `NotificationPanel.jsx` today is a fixed 360px-wide slide-over (`styles.panel`, `width: 360`) built for a flat list of mention rows and membership-invitation alerts — too narrow and too flat for Focus's grouped, multi-field rows (source, staleness, momentum, reasons, entities, primary + secondary action). Focus needs its own wide/tall `Sheet`-based panel, matching the precedent already established by `AuditDashboard.jsx`, `BrowseWorkspacesPanel.jsx`, and the now-shipped `KnowledgeExplorerPanel.jsx` (Knowledge Explorer entry, `PROJECT_PLAN.md` Section 11, 2026-07-25) — a new `FocusPanel.jsx`. Reachable via a new per-workspace icon-only trigger in `WorkspaceSidebar.jsx`'s workspace row, the same treatment "Catch Me Up"'s `Sparkles` trigger already established (icon-only button, `aria-label` carries the meaning, shown for the currently-selected workspace). `NotificationPanel.jsx` itself is not replaced — mention/invitation alerts stay exactly as they are; Focus is an additional, richer surface layered on top, and Phase 1's "Needs Your Response" category is explicitly allowed to overlap with what the mentions panel already shows (the same underlying `mention_notifications` row can appear in both, since they answer different questions: "was I mentioned" vs. "what does my judgment need to resolve").

**Scope.** Workspace-scoped, matching every other cross-channel surface in this codebase (`tasks.js`'s dashboard, `workspaceDigestService.js`'s digest, entity trending) — all are `GET /workspaces/:workspaceId/...`, gated by `requireWorkspaceMember`. A cross-workspace "everything, everywhere" aggregate is a real, larger idea (this app's own authorization and rate-limiting model is workspace-rooted throughout, so a multi-workspace merge is a materially bigger query-fan-out and privacy-surface question) and is left as an explicit open question, not silently assumed — see "Open implementation questions."

**Layout**, per Required Design Change 9:

- A concise progress summary at the top (see "Progress and completion model" for its exact composition — e.g. "3 of 5 handled · 2 decisions remain," or "You're caught up on high-priority items").
- The count of remaining high-priority obligations, separate from the total row count.
- Grouping by responsibility/state into the sections below, each collapsible, each with its own count.
- Optional filters (by workspace channel, by item type, by momentum state) — client-side over an already-fetched page for v1, no new query surface required.
- A genuine, calm, finite "caught up" state when every section is empty of actionable items — plain text, no celebratory treatment.

**Sections** (Focus categories, detailed below): Needs Your Response · Assigned to You · Waiting or Stalled · Decisions and Outcomes · Knowledge Developments · Suggested by AI · Informational (collapsed by default, visually secondary).

**Row anatomy**, every field required by Design Change 9: source (channel/DM/thread — reuses the channel-name + workspace-name display convention `NotificationPanel.jsx` and `mentionNotificationService.js`'s `mapNotification()` already use), item type, a short context excerpt (rendered through `renderMessageContent()` / `markdown.jsx` like every other piece of user content — `CLAUDE.md`: "treat all user-generated content... as untrusted when rendering"), age/staleness phrase, momentum state where applicable (with its plain-language explanation, never just a badge), "why it matters," "why you're seeing this," affected entities/projects/dependencies (as `[[Entity]]`-style chips linking to `EntityDetailsPanel.jsx`, reusing `handleOpenEntity`), a primary action, and a secondary dismiss/snooze control.

**Explicitly avoided**, per Design Change 9 and this entry's product rationale: an endless chronological feed; ranking primarily by recency; oversized cards; marketing-style summary copy; unexplained red badges; a vague unlabeled "AI insight" pill (every AI-origin row is labeled per "AI and audit requirements"); gamified streaks; celebratory effects on reaching zero.

#### Focus categories

Mapped explicitly to what backs each section, so "Phased delivery" can say precisely which categories exist after which phase:

1. **Needs Your Response** — direct questions addressed to the user, approval/decision requests where the user is the named decision-maker. Phase 1 covers only the deterministic subset reachable via explicit `@mention` + a question-shaped signal or a structured request; broader "likely unanswered question" detection is Phase 4 (AI-assisted, lands in "Suggested by AI" until confirmed).
2. **Assigned to You** — inline checkbox tasks (`- [ ] ... [owner:: @user]`, `services/taskParser.js`) where the parsed `owner` resolves to the current user and the task is unchecked. This is the one category with a real, already-shipped, deterministic backing today (`GET /workspaces/:workspaceId/tasks`).
3. **Waiting or Stalled** — threads/items the user owns, follows, or substantially participated in, where a request is outstanding or replies have stopped (see "Momentum model").
4. **Decisions and Outcomes** — confirmed decisions and their acknowledgement/follow-up state (new concept — no `decisions` table or equivalent exists today; see "Data and backend considerations").
5. **Knowledge Developments** — knowledge-graph-assisted relevance: unusual reference-frequency changes for a followed entity, new relationships, cross-channel co-occurrence (see "Knowledge-graph integration"). Entirely Phase 3.
6. **Suggested by AI** — likely unanswered questions, likely blockers, likely decisions, possible duplicates/contradictions, possible missing owners — always visually and semantically distinct from the confirmed categories above (Design Change 7). Entirely Phase 4.
7. **Informational** — collapsed, visually secondary, everything relevant-but-not-actionable (e.g. a followed entity mentioned without any of the above signals).

#### Priority model

The ranking hierarchy is adopted essentially as specified in the product direction, with an explicit note on which levels this codebase can already back deterministically and which require new state:

1. An overdue assignment owned by the user that blocks other work — **requires new state**: today's inline tasks have no due date and no "blocks" relationship (`taskParser.js`'s `parseTasks()` returns only `{index, checked, text, owner}` — no due date field exists anywhere in `messages.content`'s task syntax or any table).
2. A decision/approval/response explicitly required from the user — **requires a new concept** (no `decisions`/approval-request object exists; see below).
3. An action item assigned to the user — **exists today** via the inline-task `owner` token.
4. A direct question addressed to the user — **partially exists**: `@mention` resolution (`mentionService.js`'s `extractMentionedUserIds`) already identifies "this message was directed at you"; "is this specific message shaped like a question" does not (no question-detection today — Phase 1 can approximate with a mention that ends in `?` or similar deterministic heuristic; true detection is Phase 4 AI-assisted).
5. A confirmed blocker affecting the user's owned work — **requires a new concept** (no blocker/dependency object exists).
6. A thread where someone is explicitly waiting for the user — **requires new state** (see "waiting-on" relationships under "Data and backend considerations").
7. A thread the user owns/follows/participated in that has stalled — **requires momentum computation** (see "Momentum model") plus a definition of "follows/participated" (approximated from `messages.user_id` on a thread's messages — a user has "substantially participated" if they authored a reply in the thread; there is no explicit follow/subscribe concept today, see `conversation_follow` under "Data and backend considerations").
8. A material decision/development involving a followed project/entity/channel — **exists partially** via `entities`/`message_entities` (Phase 3, Knowledge-graph integration); "followed" itself needs a new `entity_follow`/`conversation_follow` concept.
9. General activity in a followed conversation — lowest priority, informational only, never independently promoted by volume.

**Ranking rule, stated explicitly per Required Design Change 1**: recency is a tie-breaker *within* a priority level only. Message volume is never summed into a priority score. A single approval request (level 2) always outranks a hundred-message informational thread (level 9), full stop — this is enforced structurally by grouping into priority buckets first and only ordering by staleness/recency within a bucket, not by any blended score that could let volume compensate for a lower bucket.

#### Staleness model

No universal "N hours" rule (Required Design Change 2). Staleness is computed server-side, per item type, against a configurable response window, and displayed as elapsed-responsibility language ("Waiting on you for 17 hours," "Blocked for 3 days," "No owner after 4 days") rather than a raw timestamp.

**Per-type aging basis**:

| Item type | Ages from |
|---|---|
| Direct question | The message's `created_at` (or the point a response was explicitly requested) |
| Blocker | The point it was confirmed/created |
| Action item (assigned) | Its due date, once due dates exist (see gap above); until then, its assignment time |
| Stalled thread | The point of the last unresolved request with no meaningful reply since |
| Unowned action item | The point it was identified/parsed |
| Pending decision | The point a decision-maker was named |

**Working-time awareness.** `server-generated timestamps only` is already a hard rule in `CLAUDE.md`; what does not exist today is any notion of working hours, working days, or weekends anywhere in the schema or config (`config.js` has no timezone/business-hours concept; `workspaces` has no timezone column — checked against migration `0003_layout_and_hierarchy.js`, whose `workspaces` table is only `(id, name, owner_id, created_at)`). This is a genuine gap, not an oversight to route around: a workspace-level `timezone`/`working_hours` setting (new migration, likely stored the same way other operational values live — either new `workspaces` columns or `app_settings` keys, matching the existing `app_settings`-for-non-secret-config convention from `PROJECT_PLAN.md` Section 4) is required before "17 working hours" / "2 working days" can be computed correctly rather than approximated with wall-clock hours. Until that lands, Phase 2 can ship with a documented wall-clock approximation (explicit in the UI copy, e.g. plain "17 hours" rather than "17 working hours") and upgrade the calculation once the working-time config exists — this sequencing is intentional, not a shortcut: staleness *language* should never overclaim precision the underlying data doesn't support.

**Per-channel/per-item overrides.** `channels` has no `purpose`/`topic`/incident-flag column today (checked against `0003_layout_and_hierarchy.js`: `channels` is `(id, workspace_id, name, type, created_at)`, `type` being only `PUBLIC`/`PRIVATE`/`DIRECT`/`GROUP_DM`). A channel-level response-window override (e.g., a fast incident-response channel needs a much shorter stale-threshold than an async research channel) needs a new nullable column or a `channel_settings`-style table — flagged under "Data and backend considerations." Muted/archived channels: `workspaces`/`organizations` already have `archived_at` (migrations `0008`, `0015`); channels do not have their own archival flag today, but an archived workspace's channels are already excluded from every live query via `requireWorkspaceNotArchived`-style checks, so a Focus item sourced from an archived workspace's channel should be suppressed the same way — no new mechanism needed there, just applying the existing check consistently to Focus's queries.

**Item-level overrides** (an individual decision/blocker explicitly given a longer grace period) are a natural later refinement once the base per-type/per-channel model exists; not required for Phase 2.

#### Progress and completion model

The header summary (Design Change 3) is computed, not decorative: `{highPriorityRemaining, assignedRemaining, waitingCount, decisionsRemaining, caughtUp: boolean}`, derived live from the same query set that produces the rows, never a separately-maintained counter that could drift.

**Distinct states, never conflated in the data model or API** (Required Design Change 8):

- **Read** — the user opened the Focus row's source (a view event, not a state change to the underlying object).
- **Acknowledged** — the user explicitly confirmed awareness (e.g., of a decision) without necessarily completing the underlying work.
- **Dismissed** — removed from *this user's* Focus queue only; writes no shared state. Mirrors `mention_notifications.dismissed_at`'s existing per-recipient-only semantics exactly (`mentionNotificationService.js`'s `dismissed_at` already never affects any other recipient's view).
- **Snoozed** — temporarily hidden until a timestamp or condition, then reappears automatically. Needs a `snoozed_until` (and, later, condition-based snooze) column — no existing snooze concept anywhere in this codebase to reuse.
- **Resolved** — the underlying shared obligation/blocker is complete (shared state — visible to everyone, not just the dismissing user).
- **Completed** — the underlying action item is done. For inline tasks, this already exists: `PATCH /channels/:channelId/messages/:messageId/tasks/:taskIndex` (`messages.js`) flips the checkbox via `setTaskChecked()`, audited as `MESSAGE_TASK_TOGGLED`, broadcasts `message_updated` over the channel's WebSocket room, and re-enqueues the message's embedding job. Focus's "Assigned to You" rows for inline tasks should call this exact existing endpoint as their primary "Complete" action — no new completion mechanism needed for that one item type.

**Opening a row is explicitly never sufficient to resolve an obligation** (Acceptance Criterion 4) — "Read" and "Resolved"/"Completed" are different columns/events, enforced by the state model above, not by UI convention alone.

**No backfill to keep the queue full** (Design Change 3, Acceptance Criterion 8): once a category's query returns zero actionable rows, it renders as empty/caught-up, never populated with lower-priority items to avoid looking finished. This falls out naturally from the priority-bucketed query design (each category is its own bounded query, not a fixed-size page pulled from a merged pool) rather than needing a special "don't backfill" rule bolted on afterward.

#### Momentum model

A small, explainable vocabulary — Moving, Waiting, Stalled, Dormant, Resolved — applied only to bounded work items (a thread with an identified request, a decision, a blocker, an action item), never to a channel's general activity level (Design Change 4's own example: "a busy informational channel may have no momentum state because it does not represent a bounded work item" — this is enforced by only computing momentum for rows that already qualify for one of the "Needs Your Response"/"Assigned to You"/"Waiting or Stalled"/"Decisions" categories, not for "Informational" rows).

| State | Qualifying signals | Disqualifying signals | Transitions | Deterministic or AI-assisted | Example plain-language line |
|---|---|---|---|---|---|
| **Moving** | A substantive reply/update occurred within the item's response window; no unresolved dependency currently blocks the next step | An outstanding request with no reply past its window | From Waiting, once the awaited response/approval lands; from Stalled, once a new substantive reply arrives | Deterministic (reply exists after the request, within window) | "Recent reply from Priya moved this forward." |
| **Waiting** | Progress depends on an identified response/approval/decision/assignment/external event, within its configured window | The window has elapsed (→ Stalled); the dependency is satisfied (→ Moving) | Into Waiting when a request/approval/assignment is created; out when satisfied or the window elapses | Deterministic | "Waiting for Priya for 18 working hours." |
| **Stalled** | A required dependency has exceeded its expected response/completion window | A substantive reply arrives (→ Moving); the item is explicitly resolved (→ Resolved) | From Waiting, once the window elapses; can transition directly to Moving | Deterministic | "This action item is blocking three dependent tasks and is two days overdue." |
| **Dormant** | Activity has ceased with insufficient evidence active work continues (no dependency identified, no recent reply, not explicitly resolved) | Any of: a recent reply, an identified dependency (→ Waiting/Stalled instead), explicit resolution (→ Resolved) | From Moving/Waiting after a long silence with no identified next step | AI-assisted (distinguishing "quietly finished" from "quietly abandoned" needs judgment a deterministic rule can't reliably make — flagged, not guessed at deterministically) | "No activity here in 12 days and no clear next step was identified." |
| **Resolved** | The underlying request/blocker/decision/action is explicitly marked complete | — (terminal) | From any state, only via an explicit Resolve/Complete/Acknowledge action (see "Progress and completion model") | Deterministic (it's a recorded event, not inferred) | "Marked resolved by Priya." |

**Message-frequency independence, stated as a hard rule** (Acceptance Criterion 10): the momentum classifier's inputs are *reply existence relative to a window* and *explicit resolution/dependency events*, never a raw message count. Twenty messages with no decision is still Stalled once the decision-request window elapses; one approval message moves Waiting → Moving regardless of how quiet the thread was before it.

#### Knowledge-graph integration

This app's actual knowledge graph today is `entities` + `message_entities` (migration `0019_entities.js`) + `entity_relationships` (migration `0026_entity_metadata_relationships_summaries.js`, shipped `PROJECT_PLAN.md` Section 11, 2026-07-24) plus `[[Entity Name]]` autocomplete/detail pages (`entities.js`) — a workspace-scoped bag of named things, which messages reference them, editable metadata (owner/status/tags), and a small fixed-vocabulary relationship graph between them. There is still **no "follow an entity" concept** anywhere in this codebase — the now-shipped Knowledge Explorer entry (`PROJECT_PLAN.md` Section 11, 2026-07-25) didn't introduce one either; a `entity_follow`/`conversation_follow` table remains new, unbuilt scope regardless of which entry builds it. This section is explicit about which knowledge-graph signals Focus can build *today* on top of `entities`/`message_entities`/`entity_relationships`, and which still require that follow concept (or a Focus-specific slice of it) first.

**Buildable today, on the existing `entities`/`message_entities` join shape** (the same authorized join `entities.js`'s `referencesQuery()` already uses):

- Multiple channels discussing the same entity — a `GROUP BY entity_id, channel_id` over `message_entities` joined through the caller's `channel_members`, i.e. exactly `entities.js`'s now-shipped trending query (Knowledge Explorer entry) scoped to entities the user has interacted with, restricted to a recent window.
- An entity appearing in a channel the user is authorized to access but doesn't routinely post in — detectable from the same join (the user is a `channel_members` row, so the query surfaces it; whether they "routinely monitor" it is a simple recency-of-the-user's-own-activity-in-that-channel heuristic, not a new concept).
- A new relationship between two entities — **buildable today**: `entity_relationships` now exists (shipped `PROJECT_PLAN.md` Section 11, 2026-07-24).
- "Followed entity" unusual reference-frequency increase — **requires a follow concept** (`entity_follow`, new).
- A decision in one channel affecting an action item/project elsewhere, or two discussions describing the same blocker — **requires both the decision/blocker concepts from "Data and backend considerations" and either explicit linking or AI-assisted similarity detection (Phase 4)**; the entity graph alone can suggest "these two threads both mention `[[Project Athena]]`" as a starting signal, but conflating that into "these are the same blocker" is an AI suggestion, never an automatic merge (Design Change 5's own rule: "AI or semantic similarity should not silently merge distinct blockers, decisions, or entities").
- A newly detected expert/owner for an unresolved question — the now-shipped SME endpoint (`GET .../entities/:entityId/experts`, Knowledge Explorer entry) is a direct building block Focus can call today, no need to reimplement the same `GROUP BY user_id` inline.
- A stale conversation with a relevant answer elsewhere — **Phase 4, AI-assisted** (needs semantic search over authorized content, i.e. this app's existing pgvector-backed `GET /api/search/semantic`, restricted to the asking user's authorized channels, then surfaced as a "possible" suggestion, never an automatic answer).

**Authorization, restated for this section specifically** because it is the section most likely to leak existence through aggregation if implemented carelessly: every graph traversal Focus performs must use the same inner-join-to-caller's-`channel_members` shape `entities.js`, `tasks.js`, and `workspaceDigestService.js` already establish as this codebase's structural-privacy pattern — an entity referenced only in a channel the caller can't read contributes zero rows to any Focus aggregate, count, or "unusual activity" computation, the same "absent, not zeroed" convention the now-shipped Knowledge Explorer entry already documents for trending/experts. A cross-channel "these two discussions may be related" row must never name or imply the existence of a channel the caller cannot access, even indirectly (e.g. never "also discussed in another channel" as a dangling reference — either the caller can see the linked channel, in which case name it, or the signal is suppressed entirely for that caller).

**Concrete example phrasing**, matching the product-direction examples and this codebase's existing `[[Entity]]` link convention: "Three discussions about `[[Oracle Licensing]]` now reference `[[Project Athena]]`." / "A decision in #architecture may supersede an open action item in #project-athena." — every such row must additionally satisfy the join-based authorization above before it is ever rendered.

#### Channel-health model

Distinct from the per-user Focus queue: a manager-facing view of *coordination quality* for channels the viewer is authorized to see (not a system-admin-only surface — any member with visibility into a channel can see its own health, and a manager role can see health across the channels/workspaces they administer, using the existing `WORKSPACE_ROLE_PERMISSIONS`/`requireWorkspacePermission` model rather than a new permission concept). Indicators are computed from the same underlying signals Focus itself uses (unanswered questions, overdue/unowned action items, unresolved blockers, decisions without linked follow-up, single-participant concentration, duplicate-work suggestions), never from message volume alone.

**Decomposable, not a single score** (Design Change 10's explicit requirement): if an aggregate "channel health" number is shown at all, it must expand into the underlying indicators on click — e.g. "Four direct questions have been unanswered for more than two working days," "Two confirmed decisions have no follow-up owner," "This channel has high message volume but no unresolved assigned work," "A disabled user still owns two open action items."

**A genuinely new gap worth naming explicitly**: "a disabled user still owns two open action items" requires cross-referencing task ownership (`taskParser.js`'s `owner` token, resolved to a `users` row) against `users.is_active`/disabled state — checked, `users` does carry an active/disabled flag already (used by the existing account-disable flow per `PROJECT_PLAN.md`'s WebSocket-eviction-on-disable entry), so this specific indicator is buildable today with no new schema, just a join most existing task queries don't currently perform.

Channel health is Phase 5 in this entry's phased delivery — it depends on the staleness/momentum machinery from Phases 2-3 already existing, and reuses rather than duplicates the decision/blocker/action-item concepts Phase 1-2 introduce.

#### Data and backend considerations

Reviewed against current migrations (`database/migrations/0001` through `0023`) and current services — nothing below assumes a table, route, or service that doesn't already exist unless explicitly marked **new**.

**Reusable as-is:**
- `mention_notifications` (migration `0016`, `read_at`/`dismissed_at` per-recipient) — direct-question/mention detection groundwork for "Needs Your Response."
- `messages.content`'s inline-task syntax + `services/taskParser.js` — "Assigned to You," and its existing completion path (`PATCH .../tasks/:taskIndex`).
- `entities` / `message_entities` (migration `0019`) + `entities.js`'s authorized join shape — "Knowledge Developments" (Phase 3), bounded by what's buildable without `entity_relationships` (see above).
- `message_side_effect_jobs` (migration `0020`) — the `FOR UPDATE SKIP LOCKED` polling-worker pattern (`messageSideEffectsWorker.js`) is the direct template for any new async Focus-item-generation job (e.g. AI-assisted detection in Phase 4), not a new architecture to invent.
- `channel_members`-scoped inner joins — the one and only authorization pattern every new Focus query must reuse (see "Authorization and privacy requirements").
- `app_settings` (migration `0006`) — the existing place for new non-secret operational config (default response windows, default staleness thresholds), following the same env-var-default-plus-DB-override pattern `llm.*`/`dm.autoArchiveDefaultDays` already use.

**New tables/columns this design genuinely requires** (conceptual names per the product direction; final naming should follow this codebase's existing snake_case/singular-table conventions at implementation time):

- **`focus_item_state`** (per-user, per-source-object) — `user_id`, `source_type`, `source_id`, `read_at`, `acknowledged_at`, `dismissed_at`, `snoozed_until`, timestamps. The direct analogue of `mention_notifications`' per-recipient state columns, generalized across source types instead of being mention-specific. This is where "Read/Acknowledged/Dismissed/Snoozed" live — never "Resolved/Completed," which belong on the source object itself (shared state, not per-user).
- **`decision`** (new concept, no existing analogue) — the message/thread a decision was reached in, the named decision-maker(s), `acknowledged_at` per relevant party (or a `decision_acknowledgement` join table, one row per acknowledger), optional linked action items.
- **`work_item_dependency`** (new concept) — represents "blocked by" / "waiting on" relationships between a bounded work item (task, decision, thread) and either another work item or a named person's expected response. This is what backs blocker confirmation, "waiting on you," and "blocks three dependent tasks."
- **`conversation_follow`** / **`entity_follow`** (new concept) — explicit per-user follow state for a thread or entity, since no subscribe/follow mechanism exists anywhere in this codebase today (channel membership is the closest analogue, and it's binary/structural, not a lightweight per-thread follow).
- **Due dates on action items** — today's inline-task syntax (`- [ ] text [owner:: @user]`) has no due-date token. Adding one is a `taskParser.js` regex extension (mirroring exactly how the existing `owner` token was added — same file, same "configurable alias" convention via `config.tasks.*`) plus a fixture-file update (`docs/task-tokenizer-fixtures.json`, which both `backend` and `frontend` test suites read to keep their independent tokenizers in sync — any regex change here must be mirrored in `frontend/src/markdown.jsx` exactly as the file's own header comment already requires for the `owner` token).
- **Channel-level response-window override** — a nullable column on `channels` or a small `channel_focus_settings` table (channel_id, response_window_hours, is_incident_channel, etc.) for Required Design Change 2's channel-purpose-aware staleness.
- **Workspace timezone / working-hours config** — new `workspaces` columns or `app_settings` keys (see "Staleness model" above).
- **AI-origin Focus rows** — need `origin` (`DETERMINISTIC` | `AI_SUGGESTED`), `detector_version`/`prompt_version`, and a `rejected_at`/`rejected_by` column so a user's explicit rejection of an AI suggestion is itself recorded state (Design Change 7 and Acceptance Criterion 14), distinct from a plain dismiss.

**Materialization strategy**: prefer deriving Phase 1-2 Focus rows live from source tables at request time, the same "no second system of record" principle `tasks.js`'s own header comment states explicitly ("a live projection of channel content, not a second system of record"). `decision`/`work_item_dependency`/follows are necessarily persisted (they represent real, explicit facts with no other source of truth), but the *ranked Focus feed itself* should stay a live query over that state wherever query cost allows, exactly like the tasks dashboard, rather than a separately cached/materialized feed that can drift. If a future phase needs caching for cost reasons (e.g. Phase 4's AI-assisted detection, which is expensive enough to justify persisting its output rather than re-running on every page load), invalidation must cover: new messages, replies, assignments, completions, decisions, blocker resolution, entity merges (`entity_relationships` now exists, shipped `PROJECT_PLAN.md` Section 11, 2026-07-24, but a merge/split concept on top of it does not), deleted content (no message-deletion feature exists today, per `messageSideEffectsWorker.js`'s own defensive comment, so this is forward-looking), channel membership changes, permission revocation, and user deactivation — mirroring the same "a user losing access must also lose access to any cached/derived data" rule this app already enforces structurally for mentions and digests.

#### Authorization and privacy requirements

Every one of the following is derived only from content the caller is currently authorized to access, using the established inner-join-to-`channel_members` structural pattern, not a filter applied after a broader query:

- Every Focus row, category count, progress count, health indicator, staleness calculation, momentum state, entity connection, cross-channel insight, AI input/output, explanation, and any graph traversal.
- Unauthorized private content must not leak through aggregate counts, hidden-source placeholders, inferred relationships, entity activity totals, timing side-channels, dependency counts, momentum summaries, "another channel" language, AI-generated summaries, or error behavior — matching `PROJECT_PLAN.md` Section 3's existing existence-hiding convention (not-a-member → 404, identical to a genuinely nonexistent resource) applied consistently to every new Focus surface.
- A private channel's existence must never leak through an inferred cross-channel relationship (Knowledge-graph integration's own rule above).
- A user losing access to a source (channel membership removed, workspace archived, account disabled) must also lose access to any cached/persisted Focus item derived from that source — enforced the same way `requireWorkspaceMember`'s live re-check already governs every other cross-channel query in this codebase, not by a separate cleanup job.
- System-admin structural access (`requireWorkspaceMemberOrSystemAdmin`, `membershipService.js`) must **not** implicitly grant Focus visibility into message content the admin isn't a genuine `channel_members` row for — the same explicit boundary `membershipService.js`'s own doc comments already draw ("Deliberately does NOT extend to message content... an admin who administers a private workspace this way still cannot read a single message in it"). Focus is a message-content-derived surface, so it follows the member-only path, never the structural-management override.

#### AI and audit requirements

- **Ordinary per-user Focus state — read, dismiss, snooze, local sort/filter — does not create high-volume audit rows**, matching the existing precedent that `mention_notifications.read_at`/`dismissed_at` writes, `GET .../entities/:entityId`, and the task dashboard's reads are unaudited today (pure per-user UI state, no content exposure beyond what the caller could already see, no LLM cost).
- **Shared-state changes follow the audit policy of the underlying object**: completing/reassigning an action item already writes `MESSAGE_TASK_TOGGLED` (existing); a new decision-acknowledgement or blocker-resolution action should get its own audit event type in the same style (`DECISION_ACKNOWLEDGED`, `BLOCKER_RESOLVED`, `WORK_ITEM_DEPENDENCY_CREATED`/`_RESOLVED`), following `appendAuditEvent()`'s existing shape (`actorId`, `actorIp`, `actionType`, `targetResource`, ids/counts-only `payload` — never raw message content, per `auditService.js`'s own established convention).
- **AI-assisted detection (Phase 4) reuses the existing provider abstraction end to end** — `runStreamingCompletion`, `buildXPrompt`-style prompt builders in `llm/promptTemplates.js`, `aiProxyRateLimiter`/`LLM_MAX_CONCURRENT_REQUESTS`, and the audit shape `AI_SUMMARIZE_REQUESTED`/`AI_TASK_EXTRACTION_REQUESTED`/`AI_WORKSPACE_DIGEST_REQUESTED` already establish (`provider`, `promptVersion`, `truncatedInputLength`, `wasTruncated`, source/generated item counts — never raw private content). **A real gap worth naming**: every existing AI route streams free-text/markdown back to the client and persists nothing structured (`ai.js`'s `extract-tasks` and `workspace-digest` routes are pure request/response, no stored output). Phase 4 needs the *opposite* shape — structured, individually addressable suggestion rows a user can accept/reject one at a time — so it needs either a new structured-output prompt convention (e.g. requesting JSON and parsing it server-side, with the same untrusted-output handling `CLAUDE.md` already requires for any LLM output rendered in the UI) or a per-item follow-up call pattern. This is flagged as new design work within Phase 4, not assumed solvable by reusing the streaming pattern unchanged.
- **AI suggestions are never visually or semantically equivalent to confirmed state** (Design Change 7/13, Acceptance Criterion 13) — distinct section ("Suggested by AI"), distinct `origin` column (see "Data and backend considerations"), plain-language confidence labels only ("Possible"/"Likely"/"Needs review"), never a numeric confidence percentage unless the underlying model is calibrated and that calibration has been validated (Design Change 7's explicit instruction) — this app's Ollama/vLLM adapters are not calibrated classifiers today, so numeric confidence is out of scope unless a future session does that validation work first.
- **Users can reject AI/graph-derived suggestions** (Acceptance Criterion 14) — a rejection is itself recorded (`rejected_at`/`rejected_by` on the Focus item state), and a rejected suggestion should not resurface identically on the next detection pass (the detector needs to consult prior rejections the same way it would consult prior dismissals, or risk becoming its own annoyance).

#### Metrics

Deliberately the inverse of a typical engagement dashboard, matching the product rationale above:

- Time from an item becoming stale to its resolution (should trend down).
- Count of items resolved via their primary action vs. dismissed-without-action (a high dismiss rate on a category is a signal that category's detection is miscalibrated, not that users are disengaged).
- Fraction of "caught up" states reached per user per day (a *higher* number here is success — the opposite of a typical unread-count/session-duration metric).
- AI suggestion acceptance/rejection rate, tracked per detector/prompt version (feeds directly into Phase 4's "precision and false-positive evaluation," Phase 4's own stated goal).
- **Explicitly not tracked as a success metric**: Focus panel open count, time spent in the panel, or any click-through rate — consistent with "what it should not optimize for" in the product rationale. These may still exist as basic operational telemetry (the same way any route naturally has request logs) but must never be treated as a product-health signal for this feature.

#### Phased delivery

**Phase 1 — Explicit Focus Queue** (no new AI, minimal new schema): unread direct mentions (reuses `mention_notifications` as-is); a deterministic question heuristic (explicit `@mention` + simple question-shaped signal) for "Needs Your Response"; assigned action items (reuses `taskParser.js`/`GET .../tasks` as-is); replies in threads the user authored/replied in (derivable from existing `messages.parent_message_id` + `messages.user_id`, no new table); new `focus_item_state` for per-user read/dismiss/snooze/acknowledge/complete distinctions; responsibility-based ordering per the priority model (bucketed, not a single blended score); a real finite caught-up state; "why you're seeing this" reasons drawn only from facts already computed above.

**Phase 2 — Staleness and Momentum**: configurable response windows (`app_settings`-backed defaults, per the existing config convention); working-time calculations (blocked on the workspace-timezone/working-hours gap identified above — ship with an explicit wall-clock approximation first if needed, upgrade once that config exists); overdue/stalled states; new `work_item_dependency` for explicit blocker/waiting-on relationships; due dates on inline tasks (`taskParser.js` extension + fixture sync); momentum transitions per the table above; duplicate suppression (a deterministic near-duplicate check, e.g. same entity + same channel within a short window, ahead of any AI-assisted duplicate detection in Phase 4); progress summaries.

**Phase 3 — Knowledge-Graph Focus**: `entity_follow`/`conversation_follow`; authorized cross-channel entity developments and related-discussion detection, bounded by what's buildable on `entities`/`message_entities` alone per "Knowledge-graph integration" above; linked decisions/actions (depends on Phase 2's `decision`/`work_item_dependency`); possible-duplicate-blocker surfacing (as an AI-labeled suggestion once Phase 4 lands, or omitted until then rather than guessed at deterministically); relevant-expertise discovery (reuses the now-shipped Knowledge Explorer SME query shape directly); clear graph-derived explanations, authorization-checked per-row as specified above.

**Phase 4 — AI-Assisted Triage**: likely-unanswered-question / likely-blocker / likely-decision / possible-missing-owner / possible-contradiction / possible-duplicate-work detection; requires the new structured-output AI response shape flagged under "AI and audit requirements" (a real, non-trivial addition to `llm/promptTemplates.js`/`llm/aiService.js`, not a reuse of the existing streaming-markdown pattern unchanged); user confirm/correct/reject flows; precision and false-positive tracking per "Metrics."

**Phase 5 — Channel Health**: authorized, decomposable team-level health indicators per the "Channel-health model" above; dependency/ownership analysis (including the disabled-user-still-owns-work indicator, buildable today); repeated-question and abandoned-request detection (AI-assisted, reuses Phase 4's detection infrastructure); high-volume/low-outcome detection; manager views scoped to channels the viewer already has permission over via `WORKSPACE_ROLE_PERMISSIONS`, no new permission model; trends based on coordination outcomes, never message volume.

#### Testing requirements

#### Acceptance criteria

1. A user with hundreds of unrelated unread messages but one assigned approval sees the approval ranked above general activity.
2. Every Focus row states why it matters and why the user is seeing it, in plain language, not a numeric score.
3. A direct request becomes stale according to a configured (initially wall-clock, later working-time-aware) response window, never a single hardcoded universal threshold.
4. Opening a row does not, by itself, mark the underlying obligation resolved or completed.
5. Completing the underlying action (e.g. via the existing `PATCH .../tasks/:taskIndex`) removes or updates the corresponding Focus row.
6. Snoozed items return automatically at the correct time.
7. A user can clear every explicit obligation and reach a genuine, calm caught-up state.
8. Low-value informational activity is never inserted to prevent an empty queue.
9. Momentum can transition from Waiting to Moving once the required dependency is satisfied.
10. Message volume alone never causes an item to be classified as Moving, Stalled, urgent, or high-priority.
11. A graph-derived row names the specific entity/relationship responsible for its relevance.
12. No inaccessible channel contributes to any visible row, count, momentum state, health indicator, entity trend, or AI output, for any caller.
13. AI suggestions are visually and semantically distinct from confirmed assignments, blockers, and decisions at all times.
14. A user can reject an incorrect AI or graph-derived suggestion, and that rejection is recorded and respected on future detection passes.
15. Channel health presents specific, decomposable underlying conditions, never a bare unexplained score.

### 5. Encrypted Workspace: application-managed encryption at rest for a workspace's message content

**Status**: Proposed. Not re-ranked against entries 1-4 above per this document's own maintenance rule — this is a large, standalone, security-critical feature with no dependency on any of them; where it belongs in priority order is a call for whoever is sequencing the backlog, not one this write-up makes unilaterally.
**Utility**: Today, every message in every workspace is stored as plaintext `TEXT` in `messages.content` — readable by anyone with direct Postgres access (a DBA, a stolen `pg_dump` backup file, a disk snapshot, a misconfigured replica), regardless of application-level authorization. An "Encrypted Workspace" is a workspace where that's no longer true: message content is encrypted before it ever reaches a database row, so the confidentiality of a workspace's conversations no longer depends entirely on trusting every process and person with database or backup access. For a subset of workspaces holding especially sensitive material (legal, HR, incident response, executive), this is a materially stronger guarantee than "the application enforces channel membership," which is all any workspace has today.
**Origin**: User request (2026-07-24): "a special category of workspace where all of the messages in any channel within the workspace were encrypted before being written to the database," with an explicit requirement to retain the ability to decrypt for audit purposes via "a keystore solution," accepting "even more friction" to that process as the price of stronger at-rest confidentiality, and an open question about whether vectorizing (embedding) encrypted content for semantic search/sentiment scoring is workable.

#### Threat model and scope — read this before anything else below

This is **encryption at rest with server-managed keys**, not end-to-end encryption. Getting this distinction backwards would make every other section of this design wrong, so it is stated plainly up front, and "Why not end-to-end encryption" immediately below explains why that's the correct choice given the user's own stated requirement.

**What this protects against:**
- Someone with direct Postgres access but no application session — a DBA running ad hoc queries, a compromised read replica, a leaked connection string — sees ciphertext, not conversations.
- A stolen or leaked backup file. `scripts/backup-db.sh` runs a plain `pg_dump -Fc` today with no separate encryption step — its own output already warns operators to handle the resulting file "with the same care as a database credential" (`scripts/backup-db.sh`'s existing warning text). For an encrypted workspace, the dump's `messages` rows are ciphertext; the wrapped per-workspace key stored alongside it (`workspace_encryption_keys`, below) is itself encrypted by a key that is *never* stored in the database — so the backup file, on its own, is not enough to recover plaintext. This is the actual value of envelope encryption here, stated as a concrete guarantee rather than a hand-wave.
- Disk-level exposure of the Postgres data directory (a decommissioned drive, an improperly wiped volume) — same reasoning as the backup case.
- **The system-admin structural-management path, specifically.** `authz/membershipService.js`'s `requireWorkspaceMemberOrSystemAdmin`/`requireChannelMemberOrSystemAdmin` already let a system admin administer any workspace's *structure* (create channels, add/remove members) without being a genuine member — but their own doc comments state this "deliberately does NOT extend to message content," and confirmed directly against the running code (see the research this entry is grounded on): **no endpoint today lets a system admin read message content for a channel they haven't genuinely joined.** The only way an admin reads content today is by taking the same explicit, auditable action anyone else would — adding themselves as a real `channel_members` row. For an *encrypted* workspace, this design closes that path too: joining the channel via the structural override grants visibility into ciphertext rows (ids, timestamps, sender) but not decrypted content, unless the admin separately obtains a key-access grant through the break-glass flow below. Encryption meaningfully raises the bar even against the app's own most privileged role, not just against outsiders.

**What this does *not* protect against, stated as plainly as the guarantees above:**
- **A fully compromised or malicious application server.** The running backend process must be able to encrypt and decrypt content transparently for every ordinary read/write a legitimate channel member makes — that's the whole point of the feature being usable day to day. That means the unwrapped data key for every active encrypted workspace is available in the backend process's memory during normal operation (cached the same way `search/sentimentService.js` already caches anchor-phrase embeddings at module scope). A backend process that is compromised, or a host with root access to that process, can decrypt anything the application itself could. This is the identical limitation every server-side "encryption at rest" scheme has (transparent DB encryption, LUKS disk encryption, envelope-encrypted S3 buckets with a server-held KMS role) — it is not a flaw specific to this design, but it must never be described to users as "we can't read your messages," because a sufficiently privileged operator of this deployment still can. The correct claim is narrower and still valuable: "your messages are protected from anyone who doesn't already have that level of access to the running application."
- **The AI/search/entity pipeline**, unless a workspace's owner explicitly opts back in — see "Feature interactions" below. These already send plaintext `messages.content` to the local Ollama container and/or persist plaintext-derived artifacts (embeddings, extracted entity names) in separate, unencrypted tables. Encrypting `messages.content` itself does nothing for those paths unless they're deliberately handled too.
- **A determined, well-resourced attacker who obtains the KEK/master key itself** (see "Keystore and key management" below) — the same caveat this codebase already states for `JWT_SECRET`: a leaked master secret is a full compromise of everything it protects, encryption included.

#### Why not end-to-end encryption

The user's own requirement — "I would ultimately want the ability to decrypt them for audit purposes" — already answers this. True end-to-end encryption (only client devices ever hold key material; the server never sees plaintext, not even transiently) is incompatible with a server-side audit-decrypt capability by construction: if the server can decrypt for an audit, it is not end-to-end encrypted in the sense that term is normally used. E2E encryption would also require inventing client-side key management from nothing (no such infrastructure exists in this codebase today — confirmed: no `createCipheriv`/`createDecipheriv` usage anywhere in `backend/src`, no client-side crypto in `frontend/src`) and would silently break nearly every server-side feature this app has, because they all currently operate on plaintext `messages.content` inside the backend process: `@mention` extraction and autocomplete, `[[Entity]]` extraction, inline task-checkbox parsing, semantic search, sentiment scoring, and every AI feature (summarize, extract-tasks, digest). Rebuilding all of that as client-side-computed, server-blind operations is a different, much larger project than "encrypt a workspace's messages" — out of scope for this entry, and probably its own product decision if ever wanted. Server-managed encryption at rest, with a deliberately high-friction server-side decrypt path for audit, is the design that actually matches what was asked for.

#### Cryptography

- **AES-256-GCM**, via Node's built-in `crypto` module (`createCipheriv`/`createDecipheriv`) — no new npm dependency for the core primitive. Authenticated encryption is required, not optional: GCM's auth tag means a single flipped ciphertext byte (corruption, tampering, a bug that writes to the wrong row) fails decryption loudly instead of silently returning garbage as "content."
- **Envelope encryption**: each encrypted workspace gets exactly one **Data Encryption Key (DEK)**, generated once (`crypto.randomBytes(32)`) at workspace-creation time, used to encrypt every message in every channel within that workspace. The DEK itself is never stored in plaintext — it's wrapped (encrypted) by a **Key Encryption Key (KEK)**; see "Keystore" below for what the KEK is.
- **Per-message IV**: a fresh random 12-byte IV (`crypto.randomBytes(12)`) for every single message, never reused — GCM's security guarantee depends entirely on IV uniqueness per key. At one DEK per workspace for the workspace's lifetime, the birthday-bound collision risk across any realistic message volume is negligible; a future key-rotation design (Phase 3) is the real long-term answer if a workspace's message volume ever became a legitimate concern, not a reason to complicate Phase 1.
- Ciphertext, IV, and auth tag are stored **separately** from each other (new `bytea` columns — see Schema below), not concatenated into one opaque blob, so the auth tag can be verified independently and nothing about the encoding is app-specific enough to need its own parser.

#### Keystore and key management, phased

**Phase 1 (MVP) — a single master key, matching this app's existing secret convention exactly.** `ENCRYPTION_MASTER_KEY`, a new required-if-any-encrypted-workspace-exists env var (32 raw bytes, hex- or base64-encoded), read in `config.js` the same way `JWT_SECRET` already is — `required('ENCRYPTION_MASTER_KEY', ...)`, added to `.env.example`/`backend/.env.example` with a placeholder value per `PROJECT_PLAN.md` Section 3's existing rule ("Zero hardcoding... `.env.example` files with placeholders"), never written to `app_settings`, frontend code, or committed files, for the identical reasons `JWT_SECRET`/`LLM_API_KEY`/`PGPASSWORD` already aren't. Used directly as the KEK: every workspace's DEK is wrapped with `ENCRYPTION_MASTER_KEY` via the same AES-256-GCM primitive (a KEK is just a key that happens to encrypt other keys). This is a single point of trust — stated as a real, explicit limitation, not glossed over — but it's buildable immediately, requires no new infrastructure, and is strictly stronger than today's status quo (no encryption at all). A compromised `ENCRYPTION_MASTER_KEY` is exactly as catastrophic as a compromised `JWT_SECRET` already is; this deployment's existing secrets posture already treats that class of value with real care, and this is one more value in that same class, not a new category of risk to solve for.

**Phase 2 — dual control on the *break-glass* flow specifically**, not on the KEK itself: any admin-initiated decrypt-for-audit request (see below) requires a second, distinct system admin's explicit approval before it's granted — pure application-level process control, no new cryptography, cheap to build once the break-glass flow exists at all. This directly delivers "even more friction," at the cost of nothing beyond a second `PATCH`-style approval endpoint and a `pending → approved/denied` status on the grant record.

**Phase 3 (aspirational, substantially larger scope) — threshold secret sharing for the KEK itself.** Split `ENCRYPTION_MASTER_KEY` into N shares (Shamir's Secret Sharing) distributed to N distinct key custodians (a new role, or a designated subset of system admins/org owners); reconstructing the KEK — needed once per backend process start to unwrap active workspaces' DEKs into memory, or on-demand for a break-glass event, depending on how far this phase goes — requires M-of-N custodians to each supply their share through a dedicated ceremony, never persisted together. This is the design that makes "no single person can unilaterally decrypt" a cryptographic guarantee rather than a procedural one (Phase 2's dual control is enforced by application logic; a rooted server can still bypass application logic, but cannot conjure share material it was never given). Flagged explicitly as **new engineering scope this app doesn't have today**: no Shamir's Secret Sharing library exists in this codebase's dependency tree (`npm audit`/Dependency Hygiene, `PROJECT_PLAN.md` Section 3, would need a documented reason to add one), and an unsealing ceremony is a real new operational procedure (`RUNBOOK.md` would need a new section, mirroring the care already given to `scripts/airgap-upgrade.sh`'s `CONFIRM_MAJOR_UPGRADE`-style deliberate friction). Worth building once encrypted workspaces are proven out in Phases 1-2 and there's a real second key-custodian in the picture — not a Phase 1 blocker.

#### Authorization model: two independent gates, not one

Every other access-controlled resource in this app has exactly one gate: are you a member (`requireChannelMember`/`requireWorkspaceMember`)? Encrypted workspaces need two, kept explicitly separate rather than conflated:

1. **Membership** (existing, unchanged) — governs whether a caller can see that a channel/message exists at all: list channels, list message rows (ids, timestamps, sender, *ciphertext*), receive real-time WebSocket delivery. Exactly the same `requireChannelMember`/`requireWorkspaceMember` checks every other route already uses.
2. **Key access** (new) — governs whether the server will actually decrypt a given message's ciphertext into plaintext for this specific caller. A new `workspace_key_access_grants` table (`workspace_id`, `user_id`, `granted_at`, `granted_by`, `expires_at` nullable, `revoked_at` nullable, `reason`).

The rule that makes this useful rather than just extra bookkeeping: **key access is granted automatically, at the moment of membership, for every ordinary path a member joins an encrypted workspace or one of its channels — and never automatically granted when membership was created via the system-admin structural override.** `membershipService.js`'s existing `requireWorkspaceMemberOrSystemAdmin`/`requireChannelMemberOrSystemAdmin` already return `viaSystemAdminOverride: true`/`false` from every call site — this design reuses that exact signal rather than inventing a new one: the workspace/channel-membership-creation code paths that currently insert a `channel_members`/`workspace_members` row (invitation redemption, `POST .../members`, workspace/channel creation) also insert a matching `workspace_key_access_grants` row in the same transaction, *unless* the membership was created via the structural override, in which case no grant is created and the caller gets ciphertext-only access until they separately go through break-glass. A workspace owner creating their own encrypted workspace, or a teammate accepting a normal invitation, never notices any of this — it's transparent. An admin exercising the "manage any workspace's structure" override does notice, because that's the entire point.

Decrypt-serving code (wherever `messages.content` would normally be selected and returned) checks the key-access grant for the requesting `channel_id`'s `workspace_id` before decrypting; absent a valid, non-expired, non-revoked grant, the row is returned with ciphertext metadata only (message exists, sender, timestamp) and an explicit `contentAccessDenied: true`-shaped field, never a 403 on the whole list (existence of the message itself is not the secret here; its content is) and never a silently-omitted row (that would make the channel look emptier than it is, its own kind of information leak about timing/volume).

Stated honestly, matching the Threat Model section above: this is a **software-enforced** authorization boundary, identical in kind to every other authorization check in this codebase (nothing here is more "cryptographically true" than `requireChannelMember` already is) — its value is that it's a *second*, independent check specifically for encrypted-workspace content, layered on top of the first, not a claim that it's unbypassable by a compromised server. Phase 3's threshold-KEK design is the only piece of this whole entry that would make the guarantee stronger than "the application chose to enforce this."

#### Break-glass / audit-decryption flow

New `POST /workspaces/:workspaceId/encryption/break-glass`, system-admin-gated (`requireSystemAdmin`, the same direct `is_system_admin` check `audit.js`/`adminAnalytics.js` already use — not a workspace-role check, since by definition the requester is *not* an ordinary member), requiring a mandatory `reason` string (`assertShortString`, matching `validation.js`'s existing bounded-string helpers) and an explicit `scope` (a specific message, a thread, or a bounded date range within one workspace — never "everything, unscoped," per the same minimize-blast-radius instinct `assertBoundedInt`-style caps already apply everywhere else in this codebase). Heavily rate-limited (a new `breakGlassLimiter`, low ceiling, per-admin-keyed, matching `rateLimit.js`'s established shape). Phase 1: creates a time-boxed `workspace_key_access_grants` row (`granted_by` = the admin, `reason` populated, a short `expires_at`, e.g. on the order of hours not days) and returns the requested content directly in that same response. Phase 2: the same request instead creates a `pending` grant that a *second* system admin must explicitly approve (`POST .../encryption/break-glass/:grantId/approve`) before it activates — the requesting admin cannot approve their own request.

**Audit**, matching this codebase's absolute "never log raw content" convention (`payload` logs `queryLength`/`messageCount`/`truncatedInputLength` everywhere else, never the text itself) — a new, deliberately prominent action type `ENCRYPTED_WORKSPACE_BREAK_GLASS_ACCESSED` (`actorId`, `workspaceId`, `reason`, `scope` description, `approverId` once Phase 2 lands, `expiresAt`) — never the decrypted content. Recommended, not required for Phase 1: notify the workspace's owner(s) that a break-glass access occurred (in-app notification, reusing the existing `user_notifications`/`NotificationPanel.jsx` machinery) — this app's whole design ethos is audit-log-forward and transparent rather than covert, and a workspace owner learning "an admin accessed your encrypted workspace on this date, for this stated reason" is consistent with that, not a new pattern being invented for this entry alone.

#### Schema and data model

- `workspaces.is_encrypted BOOLEAN NOT NULL DEFAULT false` — **set once, at workspace creation, and never changed afterward.** Retrofitting encryption onto a workspace with existing plaintext history is a real, separate migration problem (the plaintext already exists in every prior backup indefinitely); "decrypting" an encrypted workspace back to plain is nonsensical once real audit/compliance value is riding on the guarantee. Both directions are explicitly out of scope — a deliberate constraint, not an oversight, matching this codebase's existing "OWNER is structurally unique, never re-assignable except via an explicit transfer endpoint" precedent for other immutable-after-creation invariants.
- New `workspace_encryption_keys` (`workspace_id` PK/FK, `wrapped_dek bytea NOT NULL`, `key_version int NOT NULL DEFAULT 1`, `wrapping_key_id varchar` — which KEK/master-key version wrapped it, relevant once key rotation exists, `created_at`, `created_by`). Never stores a raw DEK.
- New `workspace_key_access_grants` (`id`, `workspace_id`, `user_id`, `granted_at`, `granted_by` nullable — null for auto-grants at membership time, an admin id for break-glass grants, `expires_at` nullable, `revoked_at` nullable, `reason` nullable). Indexed on `(workspace_id, user_id)` for the hot "does this caller have a live grant" check every content-read goes through.
- `messages` gains `content_ciphertext bytea NULL`, `content_iv bytea NULL`, `content_auth_tag bytea NULL`, `encryption_key_version int NULL`, and `content` (currently `TEXT NOT NULL`, unchanged since `0004_communication_and_content.js`) becomes nullable — an additive, non-destructive `ALTER COLUMN content DROP NOT NULL` plus four new nullable columns, consistent with this codebase's "every migration is additive, `CHANGELOG.md`'s MINOR-release rule" convention; no existing row's meaning changes. A `CHECK` constraint enforces exactly one of `content` or `content_ciphertext` is populated per row, so the two representations can never silently drift or double up. Which one a given row uses is fully determined by its channel's workspace's `is_encrypted` flag at write time — never a per-message choice.

#### Message pipeline: encrypt-on-write, decrypt-on-read, and every call site that needs to change

The blast radius here is real and worth enumerating precisely rather than waved at, since `messages.content` is read directly in more places than any other single column in this codebase. A new `services/messageEncryptionService.js` (mirroring `search/embeddingService.js`'s narrow, single-purpose shape) owns exactly two operations — `encryptMessageContent(workspaceId, plaintext)` and `decryptMessageContent(workspaceId, row)` — and every one of the following becomes a thin wrapper around it rather than reading `content` directly:

- `routes/messages.js` (message create, and the existing list/history endpoint) and `ws/server.js`'s `handleMessage` — encrypt immediately before `INSERT`, decrypt immediately after `SELECT`, in both the REST and WebSocket send paths (both already independently call `enqueueEmbeddingJob`/mention extraction today, so both already have the plaintext in hand at the moment of send — encryption slots in right after authorization, right before the insert, with zero added round trips).
- The existing task-checkbox toggle (`PATCH .../tasks/:taskIndex`, `messages.js`) — today a single-character line-level patch (`setTaskChecked`'s own doc comment: "never re-serializes anything it didn't have to"). For an encrypted message this necessarily becomes decrypt-whole → `setTaskChecked` → re-encrypt-whole (a fresh IV, since content changed) — still correct, just a different code path for encrypted rows specifically, called out explicitly rather than assumed to "just work" unchanged.
- `services/mentionNotificationService.js`'s `mapNotification()` — the `preview` field is built directly from `messages.content` (`toPreview(content)`); for an encrypted workspace's mention, this needs a decrypt step before truncating, or the preview shows ciphertext-derived garbage.
- `workers/messageSideEffectsWorker.js` — `loadMessageContext()` re-reads `messages.content` fresh from the DB (it's an async worker, not the original request), so it independently needs a decrypt step before `extractMentionedUserIds`/`linkMessageEntities` run on it. (Entity linking specifically is recommended *off* for encrypted workspaces by default — see Feature interactions below — but mention extraction, which stores no plaintext anywhere, is fine to keep running.)
- `routes/tasks.js`'s workspace task dashboard — today's `LIKE '%- [ ]%'` SQL pre-filter (`whereLikelyHasTaskLine`) cannot match anything meaningful against ciphertext bytes; it would either match nothing (task dashboard silently empty for encrypted channels) or, worse, match by coincidence. Recommended for Phase 1: encrypted channels are explicitly excluded from the task dashboard's candidate query (`AND c.workspace_id NOT IN (SELECT id FROM workspaces WHERE is_encrypted)` or equivalent), with a clear UI note why, rather than a silent, confusing empty result. A real fix (decrypt every candidate row in the window and run `parseTasks()` in application code, losing the SQL-level pre-filter's cheapness) is a reasonable Phase 2 addition, not required to ship Phase 1.

#### Feature interactions: search, entities, and AI — the vectorization question, answered directly

This is the question asked directly, so the recommendation is stated directly: **feasible, not recommended as a default, and only worth building later as an explicit, clearly-labeled opt-in — for all three of semantic search, entity extraction, and AI features, not search alone.** They share one root cause and should share one answer.

**Why not by default.** Every one of these three features works by deriving a second, separate, *unencrypted* artifact from plaintext message content and persisting or transmitting it outside the encrypted column: `message_embeddings.embedding` (a 384-dimensional vector, stored unencrypted in a `pgvector` column with an HNSW index built for fast similarity search); `entities.canonical_name`/`normalized_name`/`aliases` (extracted `[[Entity Name]]` text, stored as plain `VARCHAR`, with a `pg_trgm` GIN index for fuzzy matching); and every AI route's outbound request body to the local Ollama container (`routes/ai.js`'s summarize/extract-tasks/`workspaceDigestService.js`'s digest — all three `select` raw `content` and hand it straight to a prompt builder). Encrypting `messages.content` while leaving these three paths untouched would be actively misleading: a workspace could look "encrypted" while a `pg_trgm`-indexed, plaintext-searchable copy of its most notable extracted terms sits in the `entities` table, and while every summarize/digest request still ships the raw text to another process. **Embeddings specifically deserve a separate, sharper warning**, since the risk there is less obvious than "plaintext in another table": embedding-inversion is real, published, active research — given a vector (or query access to the model that produced it), an attacker can often reconstruct a close approximation of short source text, and chat messages are exactly the short-text regime this is most effective against. An unencrypted `message_embeddings` row for an encrypted workspace's message is not "mostly safe, just a vector of numbers" — it is a recoverable semantic fingerprint of the original content sitting in cleartext directly next to the ciphertext it's supposed to protect. Recommending it as a default would undermine the entire point of this feature.

**The default for Phase 1, therefore: encrypted workspaces get none of the three.** No `enqueueEmbeddingJob` call for messages in an encrypted channel (so no semantic search, no sentiment-trend contribution — `search/embeddingWorker.js`'s job-creation call sites gain the same `is_encrypted` check `enqueueEmbeddingJob` itself, or its callers, already need for the encrypt/decrypt work above); no `linkMessageEntities` call (so no `[[Entity]]` extraction/autocomplete/knowledge-graph participation for content inside an encrypted channel — `[[Entity]]` *syntax* can still be typed and rendered as a plain-text bracket, it just doesn't populate the cross-workspace graph); and AI routes (`summarize`, `extract-tasks`, `workspace-digest`) return a clear, explicit error (a new `ForbiddenError`-class response, not a silent no-op) rather than quietly processing content the workspace's own encryption setting says shouldn't leave the encrypted boundary.

**A reasonable, lesser-privacy fallback for search specifically, worth offering rather than leaving users with nothing:** keyword search over decrypted content, computed per-request rather than via any persisted index — bounded and paginated the same way `tasks.js`'s dashboard and `workspaceDigestService.js`'s digest already are (a rolling window, a hard cap on candidate rows), decrypting each candidate row inside the request handler and matching in application code (`String.prototype.includes`, not SQL `LIKE` against ciphertext) rather than at the database layer. Slower than the existing `pg_trgm`/HNSW-indexed paths (a bounded linear scan, not an index seek), and it persists nothing new anywhere — the search itself leaves no plaintext-derived residue once the request completes. A reasonable Phase 2 addition, not required for Phase 1.

**If semantic search over encrypted workspaces is ever a real requirement later (Phase 3+, explicit opt-in only, workspace-owner-configured):** the only version of this that doesn't reintroduce the embedding-inversion leak is encrypting the embedding vector itself with the same workspace DEK, which means giving up the HNSW index's approximate-nearest-neighbor speed — a search becomes "decrypt every candidate embedding in the caller's authorized, bounded set, then compute cosine similarity in application code," the same bounded-window tradeoff already accepted elsewhere in this codebase, not a new kind of compromise. Worth scoping as its own future entry if a workspace owner explicitly asks for it; not something this entry should build speculatively.

#### Backups and operational considerations

`scripts/backup-db.sh`'s plain `pg_dump -Fc` needs no code change for this feature to work correctly — ciphertext columns dump and restore as opaque bytes exactly like any other column, and `scripts/restore-db.sh`'s existing ACL-preservation behavior is unaffected. What operators need told explicitly (a `RUNBOOK.md` addition, not a code change): `ENCRYPTION_MASTER_KEY` is not part of the database and is never captured by a `pg_dump` — a restored database without the original master key available separately has every encrypted workspace's content permanently unrecoverable, by design. This needs to be as prominent in `RUNBOOK.md`'s backup/restore documentation as the existing "handle this file like a database credential" warning already is, stated the other direction: *losing* `ENCRYPTION_MASTER_KEY` is data loss for every encrypted workspace, exactly as real as losing the database itself.

#### Rate limiting and audit, summarized

- `breakGlassLimiter` (new, `auth/rateLimit.js`, low ceiling, per-admin-keyed) on the break-glass endpoints specifically.
- No new limiter needed for ordinary encrypted-message send/read — they ride the existing message-send/list rate limits unchanged; encryption/decryption is an in-process operation, not a new external call.
- New audit action types: `ENCRYPTED_WORKSPACE_CREATED` (workspace id, creator — routine, low-volume, matching how workspace creation itself isn't separately audited today beyond what already exists), `ENCRYPTED_WORKSPACE_BREAK_GLASS_ACCESSED` (detailed above), `ENCRYPTED_WORKSPACE_KEY_ACCESS_GRANTED`/`_REVOKED` for anything beyond the automatic at-membership grant (i.e., break-glass grants and any future manual revocation), `ENCRYPTED_WORKSPACE_BREAK_GLASS_APPROVED` once Phase 2 lands. Every payload: ids, reasons, timestamps — never content, matching the absolute existing convention with no exception carved out for this feature.

#### Testing requirements

- Round-trip correctness: encrypt then decrypt returns the original plaintext byte-for-byte, across a range of content (empty string, max-length `MAX_MESSAGE_LENGTH`, Markdown/emoji/multi-byte UTF-8).
- **Tamper detection**: a flipped ciphertext byte, a flipped auth-tag byte, or a wrong IV all fail decryption with a clear error, never silently returning corrupted "content."
- IV uniqueness isn't reused across two messages in the same workspace (a property test or a large-N sampling check, not just a single-pair assertion).
- The two-gate authorization model, as its own dedicated test class: an organic member gets full plaintext; an admin who joined via the structural override sees the message exists (ciphertext metadata) but gets `contentAccessDenied` until a break-glass grant exists; a break-glass grant expires and access reverts; Phase 2's second-approver requirement can't be satisfied by the same admin approving their own request.
- Negative-authorization tests matching `CLAUDE.md`'s standing requirement: a non-member gets the same 404 as any other workspace/channel, encrypted or not — encryption changes nothing about who can see a channel exists, only what they can read once they're in it.
- The disabled-by-default feature interactions, each with its own explicit test: no `embedding_jobs` row is ever created for a message in an encrypted channel; no `message_entities`/`entities` row is ever created from one; every AI route returns the new explicit error for an encrypted channel rather than silently succeeding.
- Backup/restore round-trip: an encrypted workspace's content, dumped and restored (matching the existing rehearsal pattern `PROJECT_PLAN.md`'s "Rehearsing the enclave upgrade script end-to-end" entry already established for a different feature), remains correctly decryptable afterward — proof the design's backup story is real, not just asserted.
- Audit-log tests confirming no payload for any of the new action types ever contains message content — the same discipline `scripts/verify-audit-log.mjs`-adjacent tests already apply elsewhere.
- `scripts/verify-audit-log.mjs` itself stays clean after the new action types are added (it verifies hash-chain structure, not payload content, so this should be a non-event, but worth confirming explicitly rather than assumed).

#### Phased delivery

**Phase 1 — Core encryption at rest, single master key, features disabled by default.** `is_encrypted` on workspace creation; AES-256-GCM envelope encryption with `ENCRYPTION_MASTER_KEY` as the KEK; `messageEncryptionService.js` and every enumerated call site updated; the two-gate authorization model with automatic at-membership key-access grants; break-glass endpoint with immediate (single-admin) time-boxed grants; encrypted workspaces excluded from semantic search, entity extraction, AI features, and the task dashboard, each with a clear "not available for encrypted workspaces" UI state rather than a silent failure; full test coverage per above; `RUNBOOK.md` backup/restore documentation updated.

**Phase 2 — Friction and recovery.** Dual-control approval on break-glass grants; keyword-search fallback for encrypted workspaces (bounded, decrypt-and-filter, no persisted index); task-dashboard support via decrypt-all-candidates-in-window instead of exclusion; workspace-owner notification on break-glass access.

**Phase 3 (aspirational) — Threshold key custody and opt-in semantic search.** Shamir's-Secret-Sharing-based KEK custody across multiple key holders; encrypted, brute-force-compared embeddings as an explicit, workspace-owner-opted-in semantic search restoration; key rotation tooling (re-wrap every workspace's DEK under a new KEK without touching message rows).

#### Acceptance criteria

1. A workspace created with `is_encrypted: true` stores every message's content as ciphertext in Postgres — confirmed by inspecting the raw row, not just by the API response looking correct.
2. A `pg_dump` of an encrypted workspace's `messages` table, inspected directly (no application involved), contains no recoverable plaintext.
3. An ordinary invited member reads and sends messages in an encrypted workspace with no different UX from an unencrypted one — encryption is invisible to legitimate use.
4. A system admin who adds themselves to an encrypted workspace's channel via the structural override sees that messages exist but cannot read their content without a break-glass grant.
5. A break-glass request without a stated reason is rejected; one with a reason succeeds (Phase 1) or enters a pending-approval state (Phase 2) and is fully audited with no content in the audit payload.
6. A break-glass grant expires and subsequent content reads for that admin revert to denied.
7. Tampering with a stored ciphertext row (flip one byte) causes decryption to fail loudly, never to return corrupted content as if it were valid.
8. No `message_embeddings`, `entities`/`message_entities`, or outbound AI request is ever created from an encrypted channel's content in Phase 1.
9. Restoring a `pg_dump` backup alongside the original `ENCRYPTION_MASTER_KEY` fully recovers every encrypted workspace's content; restoring it *without* that key recovers nothing for those workspaces — both directions demonstrated, not just claimed.
10. `is_encrypted` cannot be changed after workspace creation, in either direction, through any endpoint.

#### Open implementation questions discovered from the repository

- **Startup behavior when `ENCRYPTION_MASTER_KEY` is unset but an encrypted workspace already exists** (e.g., after a downgrade, or an operator clearing the env var by mistake). Recommended: fail closed, the same `required()` pattern `config.js` already uses for `JWT_SECRET` — but only *if* at least one encrypted workspace exists; a deployment that has never created one shouldn't be forced to set a key it doesn't need. This needs an explicit startup check against the database (does `workspaces.is_encrypted` have any `true` rows), not just an unconditional `required()` call, which is a small but real difference from every other required secret in `config.js` today and worth designing deliberately rather than copy-pasting the existing pattern.
- **Whether creating an encrypted workspace should be gated by a deployment-level toggle** (e.g., "does this deployment even want the operational complexity of key custody") independent of ordinary workspace-creation permissions — recommended: gate the *option* on whether `ENCRYPTION_MASTER_KEY` is configured at all, the same way `LLM_PROVIDER=disabled` already gates AI features off entirely for a deployment that doesn't want them, rather than a separate new permission flag.
- **Key rotation UX** (Phase 3) — rotating `ENCRYPTION_MASTER_KEY` requires re-wrapping every workspace's DEK (cheap: small values, not bulk message data) but needs a defined procedure for "what happens to a workspace whose re-wrap fails partway through" — not designed here, flagged for Phase 3 specifically rather than guessed at now.
- **Whether DMs/group DMs can ever be encrypted workspaces** — out of scope for this entry by construction: `DIRECT`/`GROUP_DM` channels have `workspace_id = NULL` (the same existing convention every other workspace-scoped feature in this codebase already excludes them by), so "encrypted workspace" as specified here structurally cannot reach them. A 1:1/group-DM encryption feature is a legitimately different, arguably even more sensitive design (no workspace-level DEK to anchor to) and would need its own entry if ever wanted — not folded into this one.
- **Whether an org owner or only a system admin should be able to initiate break-glass** — this entry recommends system-admin-only (the same actor who already holds every other structural-override capability in this codebase), but an org-scoped variant (an org owner break-glassing into an encrypted workspace within their own organization) is a plausible alternative this entry doesn't rule out, just doesn't design — worth a deliberate decision before implementation, not an assumption either way.

### Fix the `aiRoutes.test.js` audit-row race at its root

**Status**: Done — see `PROJECT_PLAN.md` Section 11, "Fix the aiRoutes.test.js audit-row race at its root" (2026-07-20). Originally ranked entry 2.

Root cause: `backend/src/llm/aiService.js`'s `runStreamingCompletion()` called `res.write(text)`/`res.end()` itself on the success path — finishing the HTTP response — and only *then* returned control to the calling route, which did `await appendAuditEvent(...)` afterward. ### Hot path splitting: async notification writes and entity linking

**Status**: Done — see `PROJECT_PLAN.md` Section 11, "Hot path splitting: async notification writes and entity linking" (2026-07-18). Before implementation, confirmed with the user that the resulting ~1s lag on mention notifications was acceptable, given the design's own text flagged this as a UX tradeoff needing direct sign-off rather than an assumption — both notification writing and entity linking moved to the worker, per that confirmation, rather than the "notifications stay sync" fallback also offered.

New migration `0020_message_side_effect_jobs.js`: `message_side_effect_jobs` (`message_id`, `job_type` — `NOTIFICATION` | `ENTITY_LINK` — composite primary key, `status`, `attempts`, `last_error`, timestamps), same `FOR UPDATE SKIP LOCKED`-polling shape as `embedding_jobs`, same grants. `routes/messages.js` and `ws/server.js`'s send paths both replaced their inline `extractMentionedUserIds`/`createMentionNotifications`/`linkMessageEntities`/mention-WS-push calls with a single `enqueueMessageSideEffectJobs(db, { messageId, workspaceId })` (new `services/messageSideEffectsQueue.js`) — a `NOTIFICATION` row is always enqueued, an `ENTITY_LINK` row only when `workspaceId` is truthy (DIRECT/GROUP_DM channels never had entity linking to begin with). New `workers/messageSideEffectsWorker.js`, structurally identical to `embeddingWorker.js`: polls on `MESSAGE_SIDE_EFFECTS_WORKER_INTERVAL_MS` (default 1s — tighter than embedding's 2s, since this feeds a user-visible notification rather than background search indexing), re-derives everything a job needs (message content, channel, workspace, sender identity) by joining `messages`/`channels`/`users` at process time rather than carrying payload columns, and — since the whole mention pipeline moved, not just the DB write — the real-time `mention` WS push (via `sendToUser`) now happens inside the worker's `NOTIFICATION` job processing, not synchronously at send time.

Three deliberate deviations from the original design text, each because the actual codebase precedent it was mirroring turned out to work differently than the design assumed:
- **No `processed_at` column, delete-on-success instead**: the design listed `processed_at` alongside `status`/`attempts`, but `embedding_jobs` — the explicitly-named template — has no such column and deletes its row on success, keeping the table free of an ever-growing "already processed" backlog. Followed `embedding_jobs`'s actual shape over the design text's `processed_at` mention.
- **No same-transaction enqueue**: the design called for the job-enqueue insert to share a transaction with the message insert. `enqueueEmbeddingJob` — the identical problem, already shipped — does not do this; it's a separate, try/catch-wrapped, best-effort insert immediately after, accepting a narrow crash window as a documented rare gap rather than a data-loss risk. Matched that precedent instead of introducing a new transactional pattern.
- **Retry/dead-letter tested via an intentionally unrecognized `job_type`, not a mocked failure**: unlike embedding jobs (which call an external provider, mockable via `global.fetch`), these jobs are pure DB work with nothing external to mock. `processJob` throws on any `job_type` other than `NOTIFICATION`/`ENTITY_LINK` — a real, deterministic error path (also useful defensively against future bad data) — and the tests insert a `'BOGUS'`-typed row directly to exercise retry/dead-letter without mocking anything.

New `disconnectUser(userId, { code, reason })` in `backend/src/ws/connectionRegistry.js` force-closes every live socket for a user (default close code `4004`, reason `"Account disabled"`, an error frame sent first since a close `reason` string isn't reliably surfaced to browser client code); `backend/src/routes/admin.js`'s `POST /users/:userId/disable` calls it synchronously right after `revokeAllRefreshTokensForUser`, in the same request as the `status: 'DISABLED'` update — not queued, since "immediately" was the whole point. That alone only handles sockets already open, so `requireAuth` (`backend/src/auth/requireAuth.js`) now re-checks `users.status === 'ACTIVE'` against the database on every REST call (previously JWT-verification-only, trusting whatever was true at token-issue time), and `ws/server.js`'s `handleAuthenticate` mirrors the identical check for both a first authenticate frame and a re-authenticate frame on an already-open socket — both paths reject with the same generic "Invalid or expired access token" message a truly invalid/expired token gets, so a disabled account can't be distinguished from either case. Separately, `new WebSocketServer(...)` gained `maxPayload: config.ws.maxPayloadBytes` (new `WS_MAX_PAYLOAD_BYTES`, default 131072/128 KiB — sized above the worst-case UTF-8 encoding of a `MAX_MESSAGE_LENGTH` message plus JSON framing overhead, so no legitimate frame is ever at risk), closing an unauthenticated memory/CPU exhaustion vector before a frame is ever buffered or reaches `JSON.parse`.

A real bug found by testing, not by inspection: exceeding `maxPayload` surfaces as an `'error'` event on the per-connection socket (`ws`'s receiver rejects the frame before `'message'` ever fires), and `wss.on('connection', ...)` had no `'error'` listener on individual sockets anywhere — an EventEmitter `'error'` event with no listener is a fatal, process-crashing exception in Node, not just a dropped event. Fixed with a no-op `ws.on('error', () => {})` per connection; `ws` already closes the socket itself (code `1009`) once it emits this, so nothing else was needed. Also updated `RUNBOOK.md`'s WebSocket Protocol close-code table with `4004` and the new payload cap.

**Tests**: `backend/tests/ws.test.js` — disabling a connected user force-closes their socket within the same test (not just on a later reconnect attempt); a disabled user's still-unexpired token is rejected on a fresh authenticate attempt; a disabled user's still-unexpired token is rejected on a re-authenticate frame sent over an already-open socket (status flipped directly via the DB in this one, isolating the reauth branch from the separate eviction path the first test covers); a frame larger than `WS_MAX_PAYLOAD_BYTES` closes the connection with code `1009`. `backend/tests/auth.test.js` gained a test proving a still-unexpired access token is rejected by `GET /api/auth/me` on the very next request after disable (previously only login/refresh were covered). 436 backend tests (435 passing, the one failure the same pre-existing `aiRoutes.test.js` audit-row race documented in prior entries — reproduced identically on a clean `main` via `git stash`, confirming it predates this change).

A handful of scoping decisions shifted the delivered shape from the original design text, each confirmed directly with the user or found necessary during implementation rather than guessed: `managers_can_archive` is an owner-delegated per-workspace toggle rather than a blanket grant; `WORKSPACE_MANAGE_MEMBERS`/`WORKSPACE_MANAGE_MANAGERS` is a real, intentional tightening of what a `MANAGER` could do versus the original flat design; ordinary workspace admins lost direct account-provisioning entirely (no workspace-scoped replacement — they fall back to invitations); `USERS_*`/`ORGS_VIEW_ALL`/`WORKSPACES_VIEW_ALL`/`SYSTEM_ADMIN_STATUS_CHANGE` were never added to the permission catalog, since every route they'd back is gated by a direct `is_system_admin` check instead, and unused constants would violate this codebase's own no-dead-abstraction convention; and `GET /workspaces/admin/all`/every `/api/admin` route deliberately bypass `requireSystemPermission`'s OWNER/MANAGER-of-any-workspace fallback (kept narrowly for AI-settings/audit continuity) in favor of a direct system-admin-only gate, to avoid an unintended cross-tenant information-disclosure widening.
